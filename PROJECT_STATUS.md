**Цель:** достоверные и воспроизводимые инженерные расчёты, а не совпадение с дипломными примерами.

## Правила ведения версий

1. После **каждого этапа с изменениями** обновить этот файл **в той же ветке**: дата, конкретные коммиты/файлы, сделано, завершено, не завершено, проверено, риски и следующий шаг.
2. Статусы не смешивать: `реализовано` ≠ `протестировано` ≠ `инженерно подтверждено` ≠ `готово пользователю`.
3. Каждый новый расчёт и каждая исправленная формула — отдельный регрессионный тест. Источник параметра указывать на уровне поля (документ, раздел/страница, модель, условия).
4. Нельзя заменять неподтверждённое паспортное число или править формулу лишь ради совпадения с дипломом.
5. Новые задачи вести в **одной** рабочей ветке, после завершения и проверок переносить в `main`; не создавать временные ветки для каждого шага.
6. Новое продолжение чата начинать чтением **этого файла**, `docs/ENGINEERING_DATA_AUDIT.md`, журнала Git и тестов.

## Выполнение этапа 2026-10-31 — после переименования

**Завершено:** обнаружено новое имя рабочей ветки, сверена доступность файлов, подтверждено количество веток; проверены основные числовые поля 17 сплавов, 17 печей и 6 стержневых машин.

**Обнаружено:** 13 печей имеют `productivity_t_h > capacity_t / melt_time_h × 1.01`; это сигнал проверки **семантики** времени плавки/продуктивности (особенно непрерывных вагранок), а не основание немедленно менять числа. Для `ZB08Y-80` по `3600×8/40` получается 720 стержней/ч, тогда как в каталоге 576; возможный коэффициент 0,8 пока не подтверждён.

**Не завершено:** техническая верификация этих записей по паспортам, полный pytest/Windows CI, проверка работы приложения. В текущем окружении прямой git-клон через сеть не доступен; сопоставление выполнялось по файлам из подключённого GitHub, а не путём запуска всего приложения.

**Исправление логики аудита:** коммиты `1d5d1c3` и `a4e708a` — проверка предела «ёмкость / время цикла» теперь применяется только к перечисленным печам периодического действия. Для непрерывных вагранок ошибочный тип предупреждения снят. Добавлены 2 регрессионных теста; запуск pytest всё ещё не подтверждён. Числа оборудования не изменены.\n\n**Следующая инженерная задача:** разделить номинальную и фактическую производительность, цикловые показатели и коэффициенты использования; проверить паспорта и условия измерения прежде, чем подключать данные к автоматическому подбору.

## Этап 2026-10-31 — автоматические тесты, требования к выпуску БД

**Запрос пользователя:** конечный пользователь НЕ должен запускать pytest, сверять коэффициенты с дипломами или самостоятельно искать паспорта оборудования. Только разработчик подтверждает данные перед включением в штатный расчёт. Числа без источника не следует называть проверенными.

**Сделано:**
- `.github/workflows/windows-exe.yml`: исправлена привязка к старому имени ветки, сборка запускается при push/PR `worck-branch` (коммит `cc72755`).
- `.github/workflows/engineering-tests.yml`: добавлен автоматический запуск полного `pytest -q --timeout=25` на GitHub Actions при изменении Python-кода или данных, а также PR и ручном запуске (коммит `977cf8c`).
- Обязанность тестировать справочники и приложение переложена на CI/разработку, а не на пользователя.

**ЕЩЁ НЕ ПРОВЕРЕНО:** первый успешный результат CI, полный локальный прогон, работоспособность Windows EXE, индивидуальные паспортные параметры большинства моделей и технологические свойства материалов. GitHub-изменение workflow само по себе НЕ является успешным тестом.

**Критерии готовности настоящей производственной БД:**
1. Каждая запись об оборудовании соответствует реальной модификации, подтверждённой первичным документом производителя или надёжным стандартом; для каждого расчётно значимого поля указаны URL/документ, конкретная таблица/страница, дата/редакция, единица и условия измерения.
2. Для сплава разделены марка и химсостав по стандарту и режимно-зависимые технологические свойства; нет автоматической подстановки среднего/придуманного числа.
3. Неизвестные данные блокируют **зависимый расчёт**, а не подменяются нулём или предположением, и должны быть видны в сводке как «нет проверенного параметра». Устаревшие учебные модели исключаются из штатного автоподбора только после безопасной реализации нового каталога и миграции.
4. Автоматические тесты, проверки источников, Windows сборка и интерактивная приёмка проходят до перевода в стабильную `main`.

**Следующие задачи:** разработать обязательную схему источников и её проверку на уровне каждого расчётного поля; провести реальную сверку первоисточников, безопасно интегрировать проверенные модели в подбор и вывести диагностические ошибки в интерфейсе. Полная БД **пока не готова**.
